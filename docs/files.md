# 文件进出（`drop`、`take`、`share`）

## 进来：`drop`

把文件拖到页面上，或者在客户机里敲 `drop` 用浏览器的文件选择框（手机上也能用），文件就出现在 `~/drop` 里。不复制：每个文件在 9p 文件系统里是一个条目，客户机读到哪里，页面就从访客的磁盘上读哪一段（`src/drop.ts`、`src/elsewhere.ts`）。几个 GB 的系统镜像，直到 fastboot 把它发给手机之前都不占地方。

客户机挂 9p 时用了 `cache=loose`，会记住目录里有什么；所以新文件先放进一个它从没见过的目录 `/.drop/<n>`，再由 hostd 改名搬进 `~/drop`，客户机自己的缓存因此始终是对的。

## 出去：`take`

```
guest@zutto-issho ~> take firmware.bin
  Saved firmware.bin, 4.0 MB.
guest@zutto-issho ~> take build/
  Saved build.zip, 12.3 MB.
```

一个文件就存成它本身；一个目录，或者好几样东西，打成一个 zip（几样东西时叫 `take-<日期>-<时间>.zip`）。电脑上的 Chrome 和 Edge 弹出保存对话框，访客选好地方，字节边读边写进去，多大的文件都不经过内存；别的浏览器（手机上的也是）先在页面里攒齐，再像普通下载一样存下来。浏览器只在访客碰页面的那一刻允许这两样，命令传到页面时那一刻多半还在；过了，屏幕上浮出一枚键，点一下就存。

**怎么做的**。`take` 在客户机里列出要存的东西：每个文件、目录和链接，它在 zip 里的名字，从哪里读，写成一个文件，再经那条带暗号的问答通道问页面（终端里显示出来的文字冒充不了，`src/ask.ts`）。页面直接从 v86 的文件系统里读这些文件，客户机的文件本来就在那里。读之前先 `sync`：刚写的文件可能还只在客户机的内存里。`/tmp` 是客户机自己内存里的 tmpfs，页面看不到，那里的东西先整个复制到页面看得到的地方。

**zip**（`src/zip.ts`）。不压缩：要拿出去的多半是镜像、压缩包、固件，压不小，而不压缩的 zip 哪台电脑都能打开。每个文件读两遍，一遍算 CRC，一遍写进去，这样每个文件头在数据之前就是完整的，不用数据描述符：Java 的 ZipInputStream 这样从头往后读的程序，碰到不压缩又带数据描述符的条目会拒绝。文件名用 UTF-8；目录和符号链接照原样存（解压到 Unix 上还是链接）；修改时间除了 zip 自己的 DOS 时间，还有一份 UTC 的。单个文件或整个 zip 过了 4 GiB 时用 ZIP64。

## 共享：`share`

```
guest@zutto-issho ~> share
  /mnt/proj  to read and to write
  share off: let go of it; the folder stays as it is
```

访客电脑上的一个文件夹，在客户机里就是 `/mnt/<它的名字>`，能读能写：在客户机里编译、改代码，改动直接落在电脑上那个文件夹里。电脑上的 Chrome 和 Edge 能让访客选文件夹；浏览器问能不能改的时候没答应，文件夹在客户机里就是只读的。`share off` 放开，或者 `share off /mnt/proj` 只放开这一个。

**列出来，按需读**。共享的那一刻把整个文件夹列一遍：目录、文件名、大小、修改时间。文件的内容要等客户机读到才从访客的磁盘上读，和拖进来的文件一样，从不整个复制进来。超过十万项的文件夹不列，共享它的一部分。共享之后在电脑上对文件夹的改动客户机看不到，再 `share` 一次就是新的样子。

**写回去**（`src/share/`）。页面接管 v86 文件系统里这个文件夹的那些 inode：

- 写和截断，写进文件夹里那个文件的一个可写流，第一次写时打开；客户机关上文件、读这个文件、或者两秒没再写时提交，电脑上才看得到。客户机写的东西先在它自己的内存里放一会儿才写到 9p 上，`/etc/rc` 把这段时间从 Linux 默认的 30 秒改成了 2 秒，开着不关的文件也很快就到文件夹里；
- 新建文件、建目录、删除、改名，在文件夹里照做一遍，按客户机做的顺序。编辑器保存时常先写一个临时文件再改名盖过原来的，也就是先删掉旧的、再把新的移过去；
- 权限、属主、修改时间、链接只在客户机里：文件夹没有这些；
- 从文件夹里改名到外面（或者从外面改名进来）算跨文件系统，页面回答 EXDEV，`mv` 自己复制再删。

**放开**。`share off` 时页面先提交没提交的、做完排着的，再放手；然后客户机才删掉它那一份列表。删的只是客户机里的那份，文件夹里的东西一个也不动。

## 测试

`npm run check:files` 只假装浏览器：电脑上 Chrome 的保存对话框，记下写给它的每个字节；没有对话框时的下载；访客选的文件夹，像浏览器的私有文件系统那样存在内存里，写的东西提交前落在文件的一份副本上，和 Chromium 一样（`scripts/lib/folder.ts`）。存下来的东西再拖回客户机，用 Python 的 zipfile 逐个验 CRC：

- 刚写的文件，存成它本身；`/tmp` 里的文件；
- 一个目录，里面有空目录和一个链接，打成 zip；几样东西一起；
- 提前用上 ZIP64 的 zip，Python 照样读；
- 没有保存对话框时下载；访客不存，说一声，客户机里什么也不留；
- 共享的文件夹：列出来、读；新建、覆盖、追加、截断、像编辑器那样保存；建目录、移进去、目录改名、删文件和目录；从外面移进来、移出去；开着不关的文件过一会儿也到了；
- 放开之后，文件夹里每个文件都还在；浏览器只让读的文件夹，客户机里写不进去。
